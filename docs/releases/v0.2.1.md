# printguard 0.2.1

Scheduled reports that print, confirm the job left the queue, and alert you when they don't.

This is a pre-homologation release. It has been tested with the simulated printer on Linux and Windows, and against a real but paused Windows print queue on a hosted CI runner. It has **not** been run against a physical printer.

## What's in it

- `printguard run`, `print-only`, `check`, `seed` and `resolve`.
- Per-day state (`ok`, `enviado`, `falha`, `unknown`) backed by a SQLite write-ahead journal. The attempt is recorded before the printer is called.
- An OS-level process lock, so two runs can't work at once.
- Recovery after a crash or reboot that checks the journal and the print queue before deciding anything. A result it can't establish stays `unknown` and is never reprinted automatically.
- A simulated printer for development and CI, and a Windows spooler backend.
- A guardian script and a scheduled task installer for Windows (08:00 daily, every 5 minutes until 09:05, boot +5 minutes, wake to run).
- Alerts as `ALERTA_<date>.txt`, with an optional Windows Event Log entry.

## Verified

- 67 tests on Ubuntu and Windows, Python 3.11 and 3.12.
- On a hosted Windows runner: the PowerShell scripts parse under 5.1 and pass PSScriptAnalyzer; the scheduled task registers with the documented triggers and settings; the spooler backend lists, cancels and finds jobs in a real queue; the guardian runs end to end. See [windows-validation.md](../windows-validation.md).

## Known limitations

- No test on a physical printer, and no test of `PrintTo` with a PDF application. The CI runner has no PDF handler.
- A job leaving the Windows queue means the spooler is done with it, not that paper came out.
- A crash before the send, or after a send that finished before the next run, ends as `unknown` and needs `printguard resolve`.
- Recovery matches jobs by file name in the spool document name. Handlers that rename the document fall back to `unknown`.
- The scheduled task, wake-from-sleep, boot trigger, repetition, and running without a logged-in user were configured but not observed firing.
- The Windows Event Log option was not verified in this release.
- The lock covers one machine and one working directory.
- The data source is a sample SQLite file. Using real data means editing `source.py` and `report.py`.
